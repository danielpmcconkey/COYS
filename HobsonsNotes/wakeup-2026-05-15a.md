## What happened last session

Trivial fix. Dan reported three consecutive `@Zazu report` failures from
this morning — all returned "I'm taking too long. Try again?" within
~2 minutes of the mention. Traced to `bin/listen:55`: the `claude -p`
subprocess had a hardcoded `timeout=120`. Zazu's morning report is now
beefy enough that 2 minutes isn't always sufficient.

Bumped the timeout from 120s to 300s. Also updated the log message
("timed out (120s)" → "timed out (300s)") for consistency. No restart
needed — `bin/listen` spawns a fresh subprocess per Discord mention,
so the new value applies immediately.

agent (Zazu, Gabi, Marcus, Pollan, etc.). The 5-minute ceiling applies
to all of them. That's fine for human-in-loop interactive agents but
worth knowing if behavior gets weird elsewhere.

## Standing corrections

- **"Stopped" is not "disabled."** User-systemd services with
  `WantedBy=default.target` survive reboot if disable was skipped. When
  retiring any background service in future, the dance is
  stop → disable → mask → remove unit file → remove data → uninstall
  binary. Verify with `systemctl --user list-units --all | grep` AND
  `pgrep -af`.
- **`/home/{agent}/` is not the agent's working directory.** The
  personality CLAUDE.md lives in `/media/dan/fdrive/codeprojects/COYS/agents/{agent}/`.
  When testing an agent interactively via `sudo -iu {agent} claude`,
  cd into the agent dir first.
- Scotty's and Marcus's CLAUDE.md tell them their scripts are "ALREADY
  BUILT. Do NOT create, modify, or debug it." This is agent-persona
  guidance. Hobson (infrastructure maintainer) can and should edit
  scripts when fixing cross-agent issues — but be explicit with Dan
  about what you're touching.
- **`bin/listen` is shared.** Any timeout/behavior change there hits
  every interactive agent. New as of this session — flag it before
  touching.
