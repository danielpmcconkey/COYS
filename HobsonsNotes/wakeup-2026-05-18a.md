## What happened last session

Trivial fix, but also a previous-session correction.

Dan reported Zazu was *still* timing out at ~2 minutes — seven consecutive
`@Zazu report` failures across three days, all returning "I'm taking too
long. Try again?" within ~2 minutes. Previous wakeup (2026-05-15a) had
bumped `bin/listen:55` from `timeout=120` to `timeout=300` and confidently
declared **"No restart needed — `bin/listen` spawns a fresh subprocess
per Discord mention, so the new value applies immediately."**

That was wrong. The `timeout=300` is a Python kwarg to `subprocess.run()`
inside the **listener** process. The listener is a long-running systemd
service. The subprocess being spawned is `claude`, but the timeout itself
is enforced by the Python listener — and the listener's bytecode was
unchanged in memory since its last restart on 2026-05-10.

`journalctl` for `coys@zazu.service` confirmed it: every post-edit log
line still read `claude -p timed out (120s)`. PID 1625 hadn't moved.

Dan ran `sudo systemctl restart coys@zazu.service coys@gabi.service
coys@marcus.service coys@pollan.service` (sudo is blocked by Hobson's
guard hook). All four came back active. Zazu's new PID was 2090795.
Dan re-tested `@Zazu report` — succeeded, "a hair over two minutes." So
the previous 120s ceiling was the actual bottleneck, and the 300s ceiling
is comfortably above the typical morning-report runtime.

## Standing corrections

- **`bin/listen` is a long-running systemd service. Edits do not take
  effect until restart.** New as of this session. The listener process
  caches its own Python bytecode in memory. Any change to
  `bin/listen` — timeouts, prompts, model selection, allowed-tools, log
  messages — requires `sudo systemctl restart coys@<agent>.service` per
  affected agent before the change is live. Always verify with
  `journalctl -u coys@<agent>.service --since <edit-time>` afterward.
- **`bin/listen` is shared across every interactive agent** (Zazu, Gabi,
  Marcus, Pollan). Behaviour changes there affect all of them, and so
  do restarts.
- **"Stopped" is not "disabled."** User-systemd services with
  `WantedBy=default.target` survive reboot if disable was skipped. When
  retiring any background service in future: stop → disable → mask →
  remove unit file → remove data → uninstall binary. Verify with
  `systemctl --user list-units --all | grep` AND `pgrep -af`.
- **`/home/{agent}/` is not the agent's working directory.** The
  personality CLAUDE.md lives in `/media/dan/fdrive/codeprojects/COYS/agents/{agent}/`.
  When testing interactively via `sudo -iu {agent} claude`, cd into the
  agent dir first.
- Scotty's and Marcus's CLAUDE.md tell them their scripts are "ALREADY
  BUILT. Do NOT create, modify, or debug it." That's agent-persona
  guidance. Hobson (infrastructure maintainer) can and should edit
  scripts when fixing cross-agent issues — but be explicit with Dan
  about what you're touching.
- **Sudo is blocked by Hobson's guard hook.** Privileged operations
  (`systemctl restart`, package installs, cron-file edits) must be
  handed to Dan to run manually. Print the exact command — don't try to
  pipe a password or work around the block.
